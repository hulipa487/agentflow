AgentFlow

A single-binary, self-hosted LLM agent runtime built in Go and Luau. Configure the ordinary; program the exceptional.

What it is

AgentFlow runs LLM-powered agents that can remember, use tools, execute shell commands, schedule background work, talk to other agents, and serve users through webhooks and Telegram. Every agent is defined declaratively in YAML; all behavior beyond the defaults comes from hot-reloadable Lua plugins that hook into versioned interfaces exposed by the core.

Design principles

  • Core provides capabilities; plugins provide behavior; YAML provides wiring.
  • One Luau state per session — actor model, message-passing only.
  • Failure defaults to truthful — unavailable tools return structured errors, never fabricated results.
  • Builtins are plugins — shipped in the binary, shadowable by name, same contract as user plugins.
  • The capability boundary is a message protocol — not a language API.

Current status: The core runtime (actors, memory, tools, shell, multi-agent, scheduler, budget, safety, metrics) is implemented and tested. Every storage backend is a real provider — SQLite, Redis, MongoDB, and PostgreSQL for KV/document storage, an in-memory volatile store for ephemeral data, and three vector stores for vector recall — pgvector, Qdrant, and Redis Stack/RediSearch (SQLite vector queries return an explicit unsupported error, never silent empties). LLM providers cover four API shapes: Anthropic Messages, OpenAI Chat Completions, OpenAI Responses, and the Gemini Interactions API, each targeting self-hosted/proxied endpoints via base_url; per-model server_tools enable provider-native server-side tools such as Google Search grounding. Channels — webhook, GitHub webhook (ghhook), and Telegram (polling, webhook, and self-configuring auto mode) — all mount on one shared HTTP listener with a built-in /health probe. An in-process mail capability (mail.imap_fetch / mail.smtp_send) resolves passwords from the credential store at call time. Multimodal is supported: channels ingest media into a content-addressed blob store (per-channel allow-list + size ceiling; filesystem or S3 backend), loops forward part descriptors into llm.chat, and the runtime resolves blob handles at request time — Chat Completions takes images + audio, Anthropic/Responses/Gemini take images + PDFs (Gemini also video, uploaded to the Gemini Files API and referenced by URI — files auto-delete after 48h). A core-owned audit journal records every inbound and outbound message (text + attachment handles) to the runtime store with a 90-day default retention. Embeddings (llm.embed, OpenAI-compatible) and cross-encoder reranking (llm.rerank) close the semantic-memory loop: pgvector stores vectors on write and builtin:semantic recall pipelines embed -> vector k-NN -> rerank. Token budgets support daily reset or rolling-window accounting, and spawn profiles carry their own shared metered pool.

Install Guide

Prerequisites

  • Go 1.25+ — the runtime is built with Go modules.
  • GNU make — drives the Luau static library + Go binary build.
  • A C/C++ toolchain for the Luau cgo bridge. The Makefile auto-selects by host OS:
    • Windows: zig (hermetic; no system gcc required).
    • Linux: system gcc (cc/c++/ar), usually from build-essential.
    • macOS: Xcode / Apple Command Line Tools (clang/clang++/ar).

Luau itself is vendored under third_party/luau/ (version 0.731, MIT), so a clean clone builds without fetching anything else.

Windows

  1. Install Go and ensure go version reports 1.25+.
  2. Install Git for Windows (includes Git Bash).
  3. Install zig and add it to your PATH.
  4. Install GNU make. The easiest route on Windows is choco install make via Chocolatey, or use the make bundled with Git Bash/MSYS2.
  5. Clone and build from Git Bash (not cmd.exe): 
    git clone https://github.com/\<you\>/agentflow.git
make            # compiles vendored Luau -> internal/vm/lib/libluau.a, then agentflow
make test       # run the Go test suite
make vet        # run go vet with cgo enabled
Important: The Makefile uses Unix shell recipes (rm -rf, mkdir -p, ./$(BIN)). If you run make from cmd.exe you will see errors such as "The system cannot find the file specified." Run it from Git Bash, or force a bash shell with make SHELL="C:\Program Files\Git\bin\bash.exe".

Linux

  1. Install Go and a C++ toolchain: 
    # Debian/Ubuntu
sudo apt update
sudo apt install -y golang-go build-essential

# Fedora
sudo dnf install -y golang gcc gcc-c++ make
  2. Clone and build: 
    git clone https://github.com/\<you\>/agentflow.git
make && make test

macOS

  1. Install Go from go.dev or Homebrew: brew install go.
  2. Install Xcode Command Line Tools: xcode-select --install.
  3. Clone and build: 
    git clone https://github.com/\<you\>/agentflow.git
make && make test

Verify the install

Save a minimal echo loop as echo.lua:

function loop()
  while true do
    local msg = session.inbox()
    session.send("echo: " .. (msg.text or ""))
  end
end

and a no-model config that wires it to a webhook as config.yaml:

version: "1"
agents:
  echo:
    loop: ./echo.lua
gateway:
  listen: ":8080"
  channels:
    - type: webhook
      path: /webhook/
      agent: echo

Run it and hit the webhook with curl:

./agentflow -config config.yaml
# in another terminal:
curl -X POST localhost:8080/webhook/ -d '{"from":"alice","text":"hello"}'

You should see echo: hello in the response. Note the trailing slash — the webhook mounts the /webhook/ subtree, and a POST to bare /webhook returns a 307 redirect that curl -d will not follow. Also check the admin endpoints and the shared listener's health probe:

curl http://127.0.0.1:9090/healthz
curl http://127.0.0.1:9090/readyz
curl http://127.0.0.1:8080/health    # shared channel listener -> {"ok":true}

Architecture

A request flows vertically through five layers: channels carry bytes in, the core authorities (safety, router, supervisor) decide where they go, per-session actors run a Luau loop, the loop calls capability-backed ops through the async bridge, and drivers reach external systems. Each layer is independently substitutable.

Multi-agent orchestration

Static agents (each with its own model + instructions) collaborate via agent.send/agent.request under can_contact ACLs; ephemeral children are spawned from profiles.agent templates with capability attenuation. A reference orchestrator (main + expert + project manager + workers) is a common pattern built on these primitives — it lives outside this runtime, in a separate product repo:

chit-chat:      user ──telegram/webhook──► main ──llm──► user

expert consult: user ──► main ──[directive: consult]──► expert_code (agent.request)
                                    ◄── opinion ── (agent.reply)
                          main ──llm (fold opinion)──► user

project launch: user ──► main ──[directive: start_project]──► agent.spawn("project_manager")
                          main ─► PM: brief{goal, channel, reply_to, chat_key}
                          PM ── decompose → store tasks ── spawn N workers
                          PM ──► worker: task      worker ──► PM: report
                          PM ──► main: {kind: milestone|decision|notify, ...}
                          main ──session.push(channel, reply_to, text)──► user  (idle-time push)
                          PM ── shutdown workers ── session.exit()

session.push (cap channel.push) is proactive egress — a background agent reaches the user without an active inbound message. session.exit terminates a spawned session cleanly (the parent receives agent.died). The orchestrator wiring and role prompts ship with the reference product repo, not this runtime.

Quick Start

Build

The Makefile compiles the vendored Luau VM bridge via cgo (zig as the hermetic C compiler), then the binary:

make        # luau static lib -> agentflow binary
make test   # go test with the cgo/zig toolchain

Run

The fastest path needs no model — a file-based echo loop replies out of the box. Point the binary at your config:

./agentflow -config config.yaml
curl -X POST localhost:8080/webhook/ -d '{"from":"alice","text":"hello"}'   # note trailing /

For an LLM-backed bot, point a real model at it (next block) and set an agent's model to that entry.

Connect a real model

AgentFlow targets Anthropic/OpenAI-compatible proxies and gateways — not the official APIs. Set base_url to your endpoint:

models:
  default:
    provider: openai          # API shape: anthropic | openai | openai-responses | gemini | rerank
    model: gpt-4o
    base_url: http://127.0.0.1:11434/v1   # Ollama / vLLM / LiteLLM / OpenRouter
    api_key: ${OPENAI_API_KEY}
    server_tools: []          # provider-native tools (gemini: google_search; openai-responses: web_search)

provider selects the request/response format. base_url selects the host. api_key may be empty for keyless local endpoints (Ollama). server_tools names provider-native server-side tools that run inside the provider's completion — the runtime injects only the native tool entry, no client-side schema.

Configuration Guide

AgentFlow is configured through a single YAML file (agentflow.yaml). Every value is validated at boot — an unknown key is a boot error with file and line, never a runtime surprise. Environment interpolation (${VAR} and ${VAR:-default}) is supported anywhere a string is accepted.

Secrets: env references, the credential store, and honest degradation

Secret-bearing fields (models.*.api_key, search.engines.*.api_key, gateway.channels[].token/secret, memory.backends.*.config.url/password/api_key, media.s3.access_key/secret_key, browser.api_token, profiles.shell.*.password) accept three forms:

  • a literal value,
  • ${VAR} (or ${VAR:-default}) — resolved from the process environment, with the credential store (by the same name) as fallback,
  • cred:<service> — resolved from the credential store only.

On the configdir path these stay as lazy references and resolve at consumer construction; on the single-file -config path the whole document is byte-expanded at load (legacy behavior, unchanged). Resolution order is env → credential store → unresolvable. The degradation policy is uniform: an unresolvable credential on an optional component (a search engine, a telegram/ghhook channel, a memory backend, the S3 media store) skips that component with a warning naming the credential — never a boot failure. A model api_key is not optional: the model stays configured and the first LLM call fails with a clear error naming the unresolved credential. runtime.credentials.enabled=false (or no store) makes cred: references unresolvable, feeding the same policy.

File skeleton

version: "1"

runtime:    { ... }   # core tuning: VM limits, workers, reload, persistence, admin
models:     { ... }   # named LLM providers
memory:     { ... }   # instance-wide backend instances
media:      { ... }   # blob store backend: fs (default) | s3
audit:      { ... }   # message journal: enabled, retention_days
profiles:   { ... }   # reusable configs: memory/, safety/, shell/, agent/
gateway:    { ... }   # channels
mcp:        { ... }   # MCP servers
tools:      { ... }   # global tool policy
agents:     { ... }   # the agents themselves
plugins:    { ... }   # plugin dir, capability ceiling

Philosophy

YAML defines topology — what exists and how it's wired. Behavior lives in Lua plugins. Parameters live in YAML. This separation means a working chatbot is a ~12-line YAML with zero code, while every point in the pipeline remains overridable.

Strict parsing: KnownFields(true) means every unknown key is a boot error. There are no "ignored" typos.

Config directories (-configdir)

As an alternative to the single file, agentflow -configdir <dir> loads a directory layout (mutually exclusive with -config). Every fragment decodes under the same strict validation, and validation runs after the merge, so cross-file references check exactly as they do in the single file. <dir> becomes the resolution base for every relative path (loops, instructions, prompt file: paths, the router route, persistence, sqlite backend paths, shell key_file, plugins.dir, media.dir).

<dir>/
  system.yaml       # required: top-level config minus agents/channels
  channels.yaml     # optional: channels: [...]
  profiles/*.yaml   # optional: one agent per file (sorted glob)
  triggers/*.yaml   # optional: triggers: [...] (merged sorted, later file wins)

A profiles/*.yaml file is an agent config plus a name and a spawn flag: spawn: false (or absent) routes it to agents, spawn: true routes it to profiles.agent (a spawn template, including its extras and credentials allow-list — spawned children see both). Agent-only fields (persistent, singleton, taps, channels, lifecycle) on a spawn profile are boot errors. A trigger is {name, event{channel, match} | cron | every, run_on_boot, target{profile}, payload} — every: and cron: triggers are executed by the engine (see triggers below), and the merged list is served to loops as data via runtime.triggers(). A -configdir deployment re-reads triggers/*.yaml on a poll, so editing a schedule takes effect without a restart.

Credential CLI

agentflow cred set|get|list|delete <name> manages engine-wide credentials in the store named by the loaded config (configdir or -config). set reads the value from an interactive prompt or stdin — never argv (pipe it: printf %s "$TOKEN" | agentflow cred set github_token). The master key comes from the env var named by credentials.master_key_env (default CREDENTIALS_MASTER_KEY); an unset key is a clear error. list prints names only, never values. These are the same records credential.get() and cred:<service> config references resolve against.

Web console

The admin server also hosts an embedded web console (on by default; -no-webui to disable) at http://<admin.listen>/ — a single-page UI for the operator, no build step or separate port. It has four tabs:

  • Dashboard — instance info, live sessions, agents/channels, an API-key manager over the credential store (per-user create/revoke, write-only secrets), and a streaming log tail.
  • Models — list every named model (key masked to a last-4 fingerprint), edit/add/remove, and a test button that makes a 1-token call through the live manager and classifies the result (auth / not_found / unreachable / …). Edits hot-apply to the running process immediately, then an explicit Persist to config writes them into the file (backup kept as .bak) and Revert reloads from the file. A drift badge shows whenever runtime and file disagree.
  • Config — a raw YAML editor with boot-equivalent Validate (strict fields, env expansion, cross-references — errors name the line), an atomic Save that backs up first and refuses if the file changed on disk underneath you, and a masked structured view. Saving prompts a restart; the runtime never silently live-reloads topology.
  • Metrics — the counters as sparklines, sampled in-process (~2h at 5s) so no external TSDB is needed; /metrics stays the Prometheus integration point.

Auth: every console API route (and /metrics, /v1/sessions, /admin/credentials) requires a bearer token — even on loopback. Set ADMIN_TOKEN to pin it; otherwise a random per-boot token is generated and printed once to the console. The static SPA files are served open but are inert without the token. Secrets are write-only throughout: list endpoints return metadata and fingerprints, never values, and the config view masks sensitive keys while preserving ${VAR} placeholders.

models — named LLM providers

models:
  default:
    provider: anthropic        # anthropic | openai | openai-responses | gemini | rerank
    model: claude-sonnet-5
    api_key: ${ANTHROPIC_API_KEY}
    base_url: ~                # override endpoint host
    timeout: 30s
    retry: 2
    max_tokens: 4096
    server_tools: []           # provider-native server-side tools

provider selects the request/response shape. base_url selects the host. For OpenAI-compatible endpoints (Ollama, vLLM, LiteLLM), include /v1 in base_url; openai appends /chat/completions and openai-responses appends /responses. For Anthropic-compatible endpoints, set base_url to the host root; the runtime appends /v1/messages. For gemini, point base_url at the version prefix (default https://generativelanguage.googleapis.com/v1beta); the runtime appends /interactions and sends the key in the x-goog-api-key header. The Gemini Interactions API is non-streaming and does not accept a token cap, so llm.stream yields one buffered delta and max_tokens is not sent. provider: rerank is a cross-encoder endpoint speaking POST {base_url}/rerank (TEI, vLLM, Jina, Cohere) and is used via llm.rerank / memory rerank_model, not as a chat model.

server_tools lists provider-native server-side tools to enable on every request (e.g. google_search on gemini, web_search/x_search on openai-responses). Unlike client-side function tools passed per-call via opts.tools, these execute inside the provider; the runtime only injects the native {type: <name>} entry. Values are provider-specific strings, keeping the runtime generic.

All three vector stores are vector-query-only, like builtin:pgvector: any other query kind is an explicit error, never a silent empty iterator. dim is fixed when the store is first created, so it must match the embedding model; changing it later needs a manual migration. builtin:redisvector stores the value beside the vector, so it also serves kv, prefix_scan and ttl; builtin:redis is unchanged and remains the plain-KV option.

A backend whose config.url/config.password/config.api_key secret reference cannot be resolved is skipped with a warning rather than failing the boot: stores bound to it rebind to a surviving backend (preferring one whose provider offers text_search, so a vector store degrades to full-text search; loops feature-detect from the binding's features) with requires lowered to what the fallback offers, or are dropped when no backend survives. A genuinely unknown backend name is still a boot error.

profiles — reusable configs

Profile kinds are namespaced: memory/<name>, safety/<name>, shell/<name>, agent/<name>. Agents reference them by short name.

Memory profile

profiles:
  memory/conversational:
    stores:
      dialogue: { backend: main_db, table: dialogue, window: 1000, retention: 30d }
      facts: { backend: main_db, table: facts, requires: [kv, text_search] }
    write: [builtin:routing_table]
    recall: builtin:recency

  memory/semantic:                        # embedding + rerank recall
    stores:
      semantic: { backend: vec, table: semantic, requires: [vector] }
    write: [builtin:routing_table]
    recall: builtin:semantic
    embed_model: embed                    # models: entry; auto-embeds writes to vector stores
    rerank_model: rerank                  # optional provider:"rerank" entry
    oversample: 4                         # fetch k*4 vector hits, rerank down to k

With recall: builtin:semantic, memory.recall({ text = "...", k = 5 }) embeds the query, runs cosine k-NN over the vector store, and reranks when rerank_model is set. Queries without text fall back to recency recall.

net — outbound connection policy

net:
  http:
    allow_private: false     # default; true disables the address guard

Governs both outbound HTTP paths — the builtin:fetch tool and the Lua http.request op — from one setting, so a deployment cannot end up with one guarded and the other not.

The guard refuses connections to loopback, RFC 1918, carrier-grade NAT, link-local (which includes the cloud metadata endpoint at 169.254.169.254), unique-local, multicast, and the reserved / special-purpose ranges. It is installed in the dialer, not checked when the URL is parsed, and that placement is the whole point: the check runs after DNS resolution and immediately before connect, so it sees the address actually being dialed. A check at parse time is defeated by DNS rebinding — the name is judged once and resolves somewhere else by the time the connection is made — and every redirect hop opens its own connection, so every hop is checked by construction.

Two details worth knowing. A zoned address (http://[fc00::1%25en0]/) is refused outright and before anything else: Go's prefix matching will not match an address carrying a zone, so without an explicit denial such an address falls through every range rule and reaches a unique-local host with the guard none the wiser. And a v4-mapped v6 address (::ffff:10.0.0.1) is unmapped before the check, since it names the same host as its v4 form.

Trade-off: the guarded transports deliberately ignore HTTP_PROXY / HTTPS_PROXY. Behind an egress proxy the dialer connects to the proxy, so the guard would judge the proxy's address and the target would never be checked at all. A deployment that egresses only through a proxy will find these paths do not use it. Also note 198.18.0.0/15 is blocked as a benchmarking range, which is the default fake-IP pool for Clash/mihomo and sing-box in TUN mode — on a developer machine running either, every proxied domain resolves into it and will be refused.

allow_private: true disables the guard entirely and logs a WARN at boot naming the risk, so it cannot be switched on silently. It exists for deployments that legitimately call an internal service; it is off by default because the guard is the only thing between a prompt-injected agent and the host's own network. The guard scopes to these two agent-controlled paths only — model, search, legal and browser drivers use admin-configured base_urls and are deliberately not covered, so an internal mirror keeps working.

Capability ceiling: plugins.allow_capabilities (global) ⊇ agents.<name>.capabilities (per-agent) ⊇ spawn-spec grants (child). You cannot delegate what you lack. If an agent omits capabilities it gets the defaults [llm.chat, memory, tools, agent.send, net.http] — note net.mail is not a default and must be declared explicitly.

Capabilities are enforced at runtime, not merely validated at boot. Each capability gates the Lua ops behind it: llm.chat → llm.*, memory → store.*, tools → tools.*, shell.exec → shell.*, net.http → http.request and os.env, net.mail → mail.*. An agent that omits one is refused with a message naming the op, the agent and the missing capability — the op stays addressable and fails clearly rather than vanishing into "attempt to call a nil value". agent.send, agent.request and agent.spawn were always enforced this way; the rest now match. runtime.* and credential.get are deliberately ungated — the first is loop machinery every agent needs, the second is already scoped by the agent's own credential list. A boot warning lists exactly what was withheld from each agent and profile. Set plugins.enforce_capabilities: false (default true) only to keep a configuration running that depended on every agent having every op.

Three builtin: vocabularies. The prefix is spelled by loops (builtin:per_chat, builtin:recency, builtin:ttl), tools (builtin:web_search, builtin:fetch, builtin:browser) and memory providers (builtin:sqlite, builtin:qdrant). They share nothing: a name from one is never valid in another's field, and nothing in the string says which it is. Two mistakes follow from that, and both are now reported — a loop: holding a tool name fails the boot with a hint naming the field it belongs in, and a skills: entry holding a loop name warns, because that one is otherwise silent (it matches no tool, is dropped, and the agent simply looks toolless). A skills: entry matching no registered tool at all is not reported, since a loop may legitimately list tools it declares itself with tool.def.

Profile extras & credentials: extras is deployment-specific, read-only profile data surfaced to the loop by agent.config() (a goal block is hoisted to a top-level goal key; everything else lands under extras). Values that are exactly a secret reference — ${VAR}, ${VAR:-default}, or cred:<service> — are never resolved for this surface: on the configdir path they stay raw and render as opaque markers ({env="VAR"} / {cred="service"}), so no resolved secret reaches a loop (or a spawned child); a string that merely embeds a reference (prefix-${VAR}) is an ordinary literal and expands as usual. credentials is the allow-list for credential.get(): an agent can only fetch a stored secret it names here; empty or missing = no access. Both fields apply to spawn profiles too and reach every child.

Daemon agents: sessions normally spawn lazily on first message. An agent with persistent: true receives a synthetic { type = "boot", from = "system:supervisor" } message once the runtime is up (after channels register), so cron schedulers and queue consumers start without external traffic.

Budget: tokens_per_day wraps LLM calls in reserve/commit/release against a token pool. By default the pool resets daily; set window (e.g. 24h, 168h) for rolling-window accounting where usage drains continuously as commits age out — no midnight cliff. A call that would exceed the budget is denied (counted in agentflow_budget_denied).

  - name: morning-digest

every: and cron: triggers are executed by the engine, not by an agent: when one is due the runtime enqueues an ordinary message into the target's mailbox —

{ id = "cron:<trigger-name>:<unix>", type = "cron", from = "system:scheduler",
  payload = { ... }, ts = ..., provenance = { kind = "scheduler", principal = "trigger:<name>" } }

— into session <target>|<trigger-name>. No agent holds a capability for this and no loop needs a timer: scheduling is engine infrastructure, so a deployment can drop the user-space scheduler agent it used to run. Deliveries always journal and count (agentflow_trigger_fires), and fire at info (debug carries the next computed occurrence).

  • every: takes a duration in ms, s, m, h, or d, compound and fractional allowed (30s, 15m, 6h, 1d, 1.5h, 2d12h). The first fire is one interval after startup (or immediately with run_on_boot); subsequent fires are anchored to that first tick, so they do not drift. The shortest interval is 100ms.
  • cron: takes the classic 5 fields (minute hour day-of-month month day-of-week) with *, N, N-M, */N, N-M/N, and comma-separated lists. Day-of-week accepts 0–7 (both 0 and 7 are Sunday). When day-of-month and day-of-week are both restricted, a day matching either fires (the classic rule). Names (mon, jan) are not supported, and there is no seconds field.
  • cron: fields are matched in runtime.timezone_offset_hours (a fixed UTC offset, default 0 = UTC). It is an offset, not a named zone, so a schedule never shifts under another region's daylight saving — 30 9 * * 1-5 with 8 means 09:30 UTC+8, every day of the year.
  • target.profile names a configured agent or a spawn profile. A spawn profile resolves to the spawn:<profile> address — a top-level session running that profile's loop, model, and grants (no parent, no capability attenuation to a parent).
  • event: triggers are not scheduled: the router and loops match those themselves. runtime.triggers() still returns the whole merged list, unchanged in shape, so loops that read it keep working.
  • A trigger that cannot be scheduled — a malformed expression, an interval under the floor, or a target.profile that is neither an agent nor a spawn profile — is logged and skipped; the rest still run. A config typo costs you one trigger and one warning line, never a boot.

Lua Plugin Development

AgentFlow plugins are plain Luau scripts. YAML defines which plugin runs for which agent; the plugin defines the behavior. There are three kinds of plugin:

  • Loop plugin — defines a global loop() function that owns the session coroutine for its lifetime. The canonical pattern is while true do local msg = session.inbox() ... end.
  • Support chunk — loaded into every session state before the loop plugin. Support chunks define globals and helper functions the loop reads. Builtins like builtin:token_budget, builtin:routing_table, builtin:recency, builtin:semantic, builtin:fact_extractor, builtin:exec_policy, and builtin:ttl are support chunks.
  • Shadow — a user plugin placed in plugins/ with the same name as a builtin. It replaces the builtin instance-wide at load time.

The async bridge

The only native primitive exposed to Luau is __af_op(json_request). It yields the coroutine; Go executes the request (inline or on a worker pool); then the coroutine resumes with (json_response, ok). The prelude wraps this raw primitive into the friendly tables documented below. Because every call yields, a busy instance stays cheap — no OS thread is blocked waiting for a model, database, or HTTP response.

-- What the prelude does for you (conceptually):
local function op(req)
  local resp, ok = __af_op(json.encode(req))
  if not ok then error(resp, 0) end
  return json.decode(resp)
end

Blocking ops include send, llm.chat, tools.run, all store.*, all shell.*, http.request, the mail.* ops, agent.*, and scheduler.*. Fast ops like inbox, log, and agent.info run inline on the actor goroutine.

Message lifecycle

session.inbox() parks the coroutine until the session mailbox receives a message. A message is a table with at least:

{
  id = "msg-...",
  type = "user",           -- "user" | "system" | "timer" | "cron" | "agent" | ...
  from = "webhook:alice",  -- core-stamped sender
  text = "hello",
  channel = "webhook",
  reply_to = "...",
  ts = 1234567890
}

session.send(text) replies through the active channel (the channel and reply target of the current message). session.push(channel, reply_to, text) sends proactively and requires the channel.push capability. session.push_user(uuid, text) pushes to a user by identity UUID. session.exit() terminates the session cleanly.

Writing a loop plugin

A minimal echo loop looks like this:

log.info("echo agent online")

function loop()
  while true do
    local msg = session.inbox()
    log.info("message from " .. (msg.from or "?"))
    time.sleep(0.3)
    session.send("echo: " .. (msg.text or ""))
  end
end

A ReAct-style loop calls an LLM and optionally tools: fetch history with memory.recall, pass tool definitions from tools.list to llm.chat, invoke any returned tool calls with tools.run, and reply with session.send. Write it as a plain loop file and point loop: at it.

scheduler — cap: scheduler

scheduler.every(interval) -> timer_id    -- seconds; dies with session
scheduler.after(delay) -> timer_id
scheduler.cron(expr) -> timer_id          -- cron subset (see below)

Timers enqueue a Message{ type = "timer" } into the owning session's mailbox — carrying msg.payload.timer_id so one session can tell its timers apart. They never call Lua from a timer goroutine, so the VM stays single-threaded. scheduler.cron supports a subset of 5-field cron: */N * * * * (every N minutes) and fixed minute/hour forms like 30 9 * * *; the day-of-month, month, and weekday fields must be *. These are session-scoped timers: they need the scheduler capability and die with the session. A deployment-wide schedule declared in YAML (every:/cron: triggers) is engine infrastructure instead — fired by the engine with no capability involved and delivered as Message{ type = "cron" }, so a loop does not have to run a timer loop to be scheduled. Use os.time()/os.date() (UTC) when a loop needs to reason about the clock itself.

tools — cap: tools

-- opts: { confirmed = true, confirm_id = "..." }

           description = "Shout the text back",

                      properties = { text = { type = "string" } },

If a tool declares needs_confirm: true, the first call returns a needs_confirm response. The runtime asks the user, then re-invokes the tool with opts.confirmed = true. Your loop sees only the final result.

tool.def declares a model-visible tool in Lua — the engine-standard replacement for hand-assembled extra tool defs. Declared tools merge into tools.list (same { type = "function", function = {...} } shape as Go tools, so they flow into llm.chat unchanged) and tools.run dispatches to the Lua handler. The handler runs synchronously on the loop coroutine and may itself call any op (llm.chat, memory.*, …). A declared name shadows a Go-registered tool of the same name in both list and run (the shadowing is applied after the skills filter, so a tool this agent cannot see never suppresses the Go tool it names). A handler error comes back as { ok = false, error = ... } instead of killing the loop. Declared tools are the loop's own code: the Go tools policy (forbidden, needs_confirm, permission: forbidden) still does not gate them. Declare at chunk top level, before loop().

Visibility: a declared tool is filtered by skills and tools.policy.default under exactly the rule that governs Go tools — listed when skills names it, hidden when skills is non-empty and omits it, all-or-nothing per default when skills is empty. That is what lets one shared loop directory carry tools only some agents get. It is a behavior change for a deployment with default: none and no skills: declared tools used to be listed unconditionally and are not now. tools.run applies the same rule — a declared name the agent cannot see falls through to the Go path and is refused as not-available, exactly as an invisible registered tool is. Registered tools were always enforced at dispatch, and tools.run is the model-facing path a hallucinated or injected tool call travels, so the two agree. A loop that wants its own handler calls the function directly.

Overriding a declared tool's text: tools.policy.overrides may name a declared tool, which moves its model-facing text out of the chunk and into config — the description (a literal, or {prompt: <key>} from the prompts registry) and params.<param>.description. The spec passed to tool.def stays the fallback when no override names the tool, and the override never touches the declared schema's types or required. Resolution happens when tools.list() is built, so a reloaded file:-backed prompt is reflected on the next call with no restart. An override never adds or removes a list entry: visibility comes from skills and the policy default, never from an override. A declared-but-hidden tool still counts as declared, so an override naming it is not reported as naming nothing.

Agents with a bound shell profile (agents.<name>.shell) also get registry tools that resolve the profile implicitly — no shell.spawn glue in the loop: builtin:shell.exec ({ command } → { ok, stdout, stderr, exit_code, duration_ms, handle_id }), builtin:shell.write ({ path, content }), and builtin:shell.destroy. The first call lazily spawns a handle from the profile; later calls reuse it; destroy tears it down (a later call spawns a fresh one). An agent without a bound profile gets honest-unavailable, and agents without the shell.exec capability do not see these tools at all, even under tools.policy.default: all. All three default to needs_confirm: true — relax per deployment via tools.policy.overrides.

builtin:fetch is the general-purpose HTTP client for APIs and plain pages, and needs no account or credential — so unlike web_search and browser it is never honest-unavailable. Options: url (required), method, headers, body (raw) or json (marshalled; sets Content-Type unless a header already does), query, timeout_ms, follow / max_redirects, user_agent, max_bytes, and insecure. It returns {ok, status, status_text, headers, body, final_url, redirects?, content_type?, content_length?, size, truncated?, tls_verified, time_cost_ms} — for any HTTP status, since a 404 is an answer the model should read rather than a tool failure; ok describes whether the request completed, status describes what the server said.

Bodies are capped (max_bytes, default 1 MiB) and the result always reports the true size and sets truncated when it cut. That bound is not a nicety: a tool result is handed to the model whole, nothing downstream truncates it, and the loop's token budgeter does not count tool results at all — so an oversized body would evict real conversation history rather than being trimmed. Destinations are subject to the net guard described above, and a refusal comes back as an error naming the address, counted as agentflow_http_private_blocked and logged against the calling agent.

insecure: true skips TLS certificate verification. It is always permitted — there is no config gate — but never silent: the skip increments agentflow_http_insecure_tls, logs a WARN naming the agent and URL, and reports tls_verified: false in the result. It skips only the certificate check; the address guard still applies, because who a peer claims to be and where the connection goes are different questions. The tool is Autonomous: true like web_search; a deployment that wants confirmation on it can set needs_confirm through tools.policy.overrides.

Wall clock. os.time() returns whole Unix seconds and takes no arguments (this is not Lua's os.time(table)). os.date() returns the date table — { year, month, day, hour, min, sec, wday, yday, isdst } with wday 1 = Sunday … 7 = Saturday, yday 1–366, and isdst always false — and takes an optional Unix-seconds time (default: now). Error handling

Always wrap external calls in pcall so a sick provider or bad command does not crash-loop the session:

local ok, reply = pcall(llm.chat, messages, { model = info.model })
if not ok then
  log.warn("llm.chat failed: " .. tostring(reply))
  session.send("⚠️ I couldn't reach my model right now.")
  return
end

The bridge returns errors as JSON strings; the prelude unwraps them so stack traces point to your code, not the prelude.

Confirmation and permissions

Tools and shell builtins can declare needs_confirm. The first tools.run returns a result with needs_confirm = true and a confirm_id; the actor asks the user, then re-invokes the tool with opts.confirmed = true and the same confirm_id. Your loop sees only the final result, so in most cases you do not need to handle confirmation manually.

Restrictions and caveats

  • llm.stream returns a closure — call it directly, never in a generic for ... in.
  • The standard library includes base, coroutine, table, string, math, bit32, utf8, and buffer. io and debug are not available, and neither is the real os library: the prelude provides exactly os.env, os.time, and os.date (all UTC — there is no local timezone in the sandbox).
  • Raw network access from Lua is only through http.request and the mail.* ops. There is no socket library. The HTTP paths — this op and the builtin:fetch tool — refuse private, loopback, link-local and reserved destinations in the dialer, so a URL is not enough to reach the host's own network; see the net block. mail.* is not covered by that guard and still dials whatever host the loop names.
  • All values crossing the bridge are JSON-encoded. Tables must be serializable; functions and userdata cannot cross.
  • Plugins are hot-reloadable when runtime.reload.watch is true. Edits to a loop file or instructions file restart the session coroutine from scratch on the next turn.

Practical examples

Drop any of these into a loop file and point an agent's loop: at it:

Tool loop

function loop()
  while true do
    local msg = session.inbox()
    if msg.type == "user" and msg.text then
      local info = agent.info()
      local tools = tools.list()
      local ok, reply = pcall(llm.chat,
        { { role = "user", content = msg.text } },
        { model = info.model, tools = tools, tool_choice = "auto" })
      if ok and reply.tool_calls then
        for _, tc in ipairs(reply.tool_calls) do
          local r = tools.run(tc.name, tc.args)
          log.info("tool result: " .. json.encode(r))
        end
        session.send(reply.text or "done")
      elseif ok then
        session.send(reply.text or "")
      else
        session.send("error: " .. tostring(reply))
      end
    end
  end
end
